# ResourceBar 설계 메모

Stats(같은 맥에서 코어 하나의 약 5.7%)를 대신하려고 만든 가벼운 메뉴 막대 리소스 모니터.
실제로 보는 것만 넣고, 그리기 비용을 재 가며 구조를 정했다. 측정은 2026-11-04, 14" MacBook Pro(Apple Silicon),
macOS 26.6, 화면 2대(내장 + 외장) 기준이다.

## 1. 메뉴 막대 (칸 1개, 왼쪽부터)

| 위젯 | 값 | 모양 |
|---|---|---|
| SSD | 실제 사용률 = 1 - f_bavail/f_blocks (`/System/Volumes/Data`). 비울 수 있는 공간을 여유로 치지 않는다 | 세로 막대. 80% 미만 systemBlue, 80% 이상 systemOrange, 90% 이상 systemRed |
| GPU | IOAccelerator `PerformanceStatistics`의 `Device Utilization %` | 선 그래프 + 반투명 채움, systemBlue |
| CPU | 전체 코어 평균 사용률(`host_statistics`의 tick 차이) | 선 그래프 + 반투명 채움, systemBlue |
| RAM | (앱 메모리 + 고정 + 압축) / 전체 | 선 그래프 + 반투명 채움, systemOrange |
| 네트워크 | 업로드·다운로드 bytes/s (lo 제외 모든 인터페이스 합, 64비트 계수기) | 빨강 ↑·파랑 ↓ 화살표 + 두 줄 글자("28 KB/s") |

- 1초마다 갱신한다. 그래프 이력은 60점이고, 시작할 때 첫 값으로 60점을 채워 바로 정상 모양으로 그린다.
- 배치·크기는 `ResourceBar/BarLayout.swift`. 위젯마다 세로 작은 라벨(S/S/D, G/P/U, C/P/U, R/A/M)과 얇은 둥근 테두리. 칸 폭은 228pt로 고정한다.
- 색은 동적 시스템 색을 그리는 순간의 외관으로 풀어 쓴다. `effectiveAppearance`를 KVO·알림으로 관찰해서 다시 그리지 않는다. 이 저장소의 다른 세 앱이 "외관 관찰 → 그림 → 외관 관찰" 무한 반복으로 코어 하나를 99% 쓴 적이 있다(커밋 10a2da8).
- **칸을 하나로 합친 이유.** 화면이 2대면 AppKit이 칸을 다시 그릴 때마다 다른 화면 메뉴 막대용 복제본을 새로 찍는다(`-[NSStatusItem _updateReplicants]` → `cacheDisplayInRect`). 노치 때문에 내장 화면에서 칸이 안 보여도 찍는다. 처음 시험에서 이게 그리기 비용의 약 90%였다. 위젯마다 칸을 따로 두면(Stats 방식) 2.03%, 한 칸에 다섯 위젯을 그리면 1.18%였다.
- 레이어(Core Animation)로 그리는 방식도 시험했다. 표준 방식보다 코어 하나의 0.1%p쯤 가벼웠지만(7번 짝 비교 중 6번), 복제 칸을 갱신하려면 문서에 없는 AppKit 동작에 기대야 하고, 그 동작이 바뀌면 다른 화면의 칸이 조용히 멈춘다. 그래서 넣지 않았다.

## 2. 왼쪽 클릭 → 누른 위젯의 창

`NSPopover`를 누른 위젯 아래에 띄운다. 창 밖을 누르거나 같은 위젯을 다시 누르면 닫힌다. 앱을 활성화하지 않아서 쓰던 앱의 키보드 포커스를 뺏지 않는다.

| 누른 위젯 | 창 내용 |
|---|---|
| CPU | 최근 5분 큰 그래프 + CPU를 많이 쓰는 프로세스 8개(이름·PID·%) + 종료 버튼 |
| GPU | 최근 5분 큰 그래프 + 렌더러·타일러 사용률. GPU가 쓰는 메모리가 읽히면 한 줄 더 |
| RAM | 최근 5분 큰 그래프 + 앱·고정·압축·캐시된 파일, 스왑, 메모리 압박(정상·경고·위험) + 메모리를 많이 쓰는 프로세스 8개(footprint) + 종료 버튼 |
| SSD | 사용량 한 줄(사용 GB / 전체 GB, 실제 여유 GB) + 디스크 읽기·쓰기를 많이 하는 프로세스 8개(초당 바이트) + 종료 버튼 |
| 네트워크 | 최근 5분 업로드·다운로드 그래프와 현재 값만 |

- 프로세스 목록은 창이 열려 있을 때만 2초마다 갱신하고, 닫히면 멈춘다. 평소에는 프로세스를 훑지 않는다.
- 종료 버튼: 확인 창("<이름>(PID n)을 종료할까요?") 뒤에 SIGTERM. 확인 창에서 Return은 "종료", Esc는 "취소"다. 이 키가 확인 창으로 가도록 종료 버튼을 누를 때만 앱을 활성화한다(`--open` 실행에서는 하지 않는다). 보내기 직전에 그 PID의 시작 시각과 소유자를 다시 읽어, 그사이 끝났거나 PID가 다른 프로세스에 재사용됐으면 보내지 않는다. 내 계정 소유가 아니거나 launchd·kernel_task·자기 자신이면 버튼을 끈다.
- loginwindow도 버튼을 끈다. 내 계정 소유지만 로그인 세션 자체라 종료하면 그 자리에서 로그아웃된다. Dock·Finder·ControlCenter·SystemUIServer는 막지 않는다. 종료해도 macOS가 곧바로 다시 띄우므로, 멈추거나 CPU를 계속 쓸 때 다시 띄우는 데 쓸 수 있다.
- 창 바탕은 불투명하게 깐다. macOS 26의 유리 재질은 뒤 화면이 비쳐서, 뒤가 어두우면 글자가 거의 안 보였다.

### 다른 계정의 프로세스

일반 권한의 앱은 다른 계정(root, `_windowserver` 등) 프로세스의 사용량을 읽을 수 없다(`proc_pid_rusage`가 EPERM). 이 맥에서는 전체 650개 중 약 170개에서 230개였고, WindowServer처럼 문제를 일으키는 쪽이 대개 여기 있다.

- CPU·메모리 창이 열려 있는 동안(2초마다 1번)과 기록 줄을 남길 때(1초 간격 2번)만, 직접 못 읽은 PID들을 `/bin/ps -o pid=,time=,rss= -p <PID들>`에 넘겨 받는다(셸 없이 `posix_spawn`). `ps`는 setuid root라 이 값들이 보인다. 목록·이름·시작 시각은 원래 읽히고, 못 읽는 것은 사용량이다.
- CPU %는 두 `ps` 결과의 CPU 시간 차이로 낸다. `ps`의 시간은 1/100초 단위라 이 줄의 값은 계단으로 나온다(2초 간격이면 0.5%).
- PID 재사용은 `sysctl KERN_PROC_PID`의 시작 시각(다른 계정 것도 읽힌다)으로 가린다. 이름은 `proc_pidpath`로 새 PID일 때만 찾는다.
- 그 줄은 종료 버튼 자리에 "(시스템)"을 표시하고 종료할 수 없다.
- 메모리는 `ps`의 RSS라 footprint와 기준이 다르다. 압축·그래픽 메모리가 빠져 대개 작게 나온다(WindowServer: RSS 107MB, 활성 상태 보기 549MB). 그래서 메모리 목록에는 거의 올라오지 않는다.
- SSD 창에서는 돌리지 않는다(`ps`가 디스크 읽기·쓰기를 주지 않는다). `kernel_task`는 `ps`에도 없다.
- `top`은 setuid지만 1번에 CPU 약 1초를 써서 쓰지 않는다.
- `ps` 시한 2초: 넘기면 SIGKILL로 끝내고 그 표본은 시스템 프로세스 없이 간다(창 안내 문구가 바뀐다). 끝낸 `ps`를 거두지 못했으면 거둘 때까지 새로 띄우지 않는다. rss가 0인 줄(실제로는 못 읽은 것)은 버린다.

## 3. 오른쪽 클릭(또는 control-클릭) 메뉴

메뉴 순서대로:

- **메뉴 막대 오른쪽 끝에 고정**(기본 켜짐). 칸 폭이 228pt라 노치 화면에서는 오른쪽 끝 말고 들어갈 자리가 없다. 구현은 `Shared/Shared.swift`의 `StatusIcon`과 같은 방식이다([macos-notes.md 14절](macos-notes.md#14-상태-항목을-오른쪽-끝에-고정하는-옵션-만들기)).
- **기록 폴더 열기**
- **로그인 시 자동 실행** (`SMAppService.mainApp`, 다른 앱들과 같다)
- (구분선) **종료**

## 4. 기록 (한도를 넘을 때만 그 순간의 상위 프로세스를 남김)

- 한도: CPU 전체 80% 이상이 10초 지속, GPU 80% 이상이 10초 지속, 메모리 압박 "경고" 이상(`sysctl kern.memorystatus_vm_pressure_level` 값 2 이상, 4는 "위험").
- 판정은 매초 이미 읽는 값으로만 한다. 한도 아래에서는 비교 몇 번 말고 추가 비용이 없다.
- 남기는 것(JSON 한 줄): 시각, 이유, CPU·GPU·RAM 값, 메모리 압박, CPU 상위 10개(1초 간격 두 표본으로 %), 메모리 상위 10개(footprint), 디스크 쓰기 상위 5개. 두 표본 모두 다른 계정 프로세스를 `ps`로 함께 받는다. 그 항목은 `"system": true`이고 메모리 키가 `rss_mb`다(보통 항목은 `footprint_mb`). `processes_via_ps`는 `ps`로 받은 수, `processes_unreadable`은 그래도 못 읽은 수(kernel_task 등).
- 파일: 홈 폴더의 `Library/Logs/ResourceBar/spikes-YYYY-MM-DD.jsonl`. 30일 지난 파일은 시작할 때와 날짜가 바뀔 때 지운다.

### 반복 규칙

메모리 압박이 평소에도 "경고"인 맥이 많다. 경고에 1분마다 줄을 남기면 하루 종일 같은 줄이 쌓인다. 그래서 이유별로 나눴다.

- CPU·GPU·압박 "위험": 새로 시작되면 바로 한 줄, 이어지면 60초마다.
- 위험 줄은 60초에 한 번을 넘지 않는다(처음 위험은 바로). 위험은 지속 조건이 없어서, 4와 2를 오가면 12초마다 줄이 생길 수 있었다.
- 압박 "경고"만: 새로 시작되면 한 줄, 이어지면 10분마다. 경고 줄은 10분에 한 번을 넘지 않는다(경고가 꺼졌다 켜졌다 해도 직전 경고 줄에서 10분이 안 됐으면 건너뛴다).
- 줄 하나에는 그 순간 한도를 넘은 이유를 모두 적고, 그 줄에 든 이유는 모두 방금 남긴 것으로 친다.
- 이유가 10초 연속으로 없어야 그 이유가 끝난 것으로 본다. 그 전에 다시 넘으면 같은 에피소드다. CPU·GPU는 "10초 지속"을 새 에피소드를 열 때만 요구하고, 진행 중에는 한도 위인 tick이면 이어지는 것으로 본다. 이게 없으면 2초만 내려갔다 올라도 매번 새 시작 줄이 생긴다. "N초 지속"은 한 tick 하락을 봐준다.
- `kind`는 줄 단위다. 그 줄에 지금 에피소드에서 처음 드는 이유가 하나라도 있으면 `start`. 위험인지는 `memory_pressure_level` 4로 본다. 경고 줄이 10분 하한 때문에 늦게 남으면 `start`라도 `time`은 늦은 시각이다.
- 한계: 앞 줄을 쓰는 동안(약 1초) 판정을 보류하므로, 그 1초에만 있었던 이유는 줄 없이 지나갈 수 있다.

## 5. 넣지 않은 것

온도(팬 제어 앱이 이미 보여 준다), GPU 게이지, CPU 코어별 사용률·주파수, Neural Engine·FPS, 디스크 건강·볼륨별 용량·읽기쓰기 누적, 네트워크 IP·와이파이·연결 상태(핑)·프로세스별 사용량, 센서·팬, 알림, 꾸미기 설정(칸 모양 선택·칸 합치기·갱신 주기 설정). 네트워크 요청과 관리자 권한도 쓰지 않는다.

## 6. 실행 인자

| 인자 | 뜻 |
|---|---|
| `--login-item on\|off` | 로그인 항목을 켜거나 끄고 바로 끝낸다(메뉴를 누를 수 없는 설치 스크립트용). 결과(`on`·`off`·`requires-approval`)를 찍는다. 바꾸지 못하면 stderr에 이유를 쓰고 종료 코드 1, 값이 없거나 틀리면 앱을 띄우지 않고 2로 끝난다 |
| `--duration N --warmup W` | W초(빼면 3초) 뒤부터 N초 동안 자기 CPU를 재고, 끝나면 stdout에 JSON 한 줄을 찍고 끝낸다 |
| `--open ssd\|gpu\|cpu\|ram\|net` | 시작하자마자 그 창을 연다. 앱을 활성화하지 않고, 창 밖 클릭으로 닫히지 않는다 |
| `--spike-test` | 기록 한도를 아주 낮춰(CPU·GPU 1%를 3초) 기록 기능을 시험한다 |
| `--log-dir PATH` | 기록 폴더를 바꾼다. 시험할 때는 실제 기록 폴더를 더럽히지 않게 쓴다 |
| `--no-pin` | 이번 실행에만 오른쪽 끝 고정을 끈다 |

`--duration` JSON 필드(출력은 키 이름순): `cpu_pct`(앱 자신, 코어 하나 기준 %), `cpu_children_pct`(앱이 띄운 `ps`), `cpu_total_pct`(둘의 합), `cpu_user_s`, `cpu_sys_s`, `wall_s`, `ticks`, `renders`, `replica_refreshes`(지금 렌더러에서는 늘 -1), `phys_footprint_mb`, `main_screen`(본 칸이 놓인 화면), `main_screen_scale`, `main_window_visible_ratio`, `replica_visible_ratio`(다른 화면 복제 칸이 보인 tick 비율, 모르면 -1), `popup`, `spike_events`, `renderer`(늘 `standard`).

## 7. 측정

같은 맥, 같은 시간대에 60초씩 재고 Stats는 같은 구간의 `ps` CPU 시간 차이로 쟀다. 모두 코어 하나 기준이다.

| 상태 | ResourceBar | Stats 3.0.24 |
|---|---|---|
| 평소(메뉴 막대만) | 0.90에서 1.09% (7번 중앙값 1.00) | 5.19에서 5.99% (중앙값 5.69) |
| CPU 창을 열어 둔 동안 | 2.86, 2.94% (그중 `ps` 0.52, 0.53) | |
| 메모리 창을 열어 둔 동안 | 2.37, 2.49% (그중 `ps` 0.52, 0.54) | |
| 메모리(footprint) | 13MB, 창을 열면 약 29MB | 201MB |

- 그리기 없이 값 읽기만 돌리면 앱 전체가 코어 하나의 0.10%다. 그중 값 읽기 자체는 1번에 약 65µs다. 나머지는 거의 그리기와 복제본 스냅샷이다.
- `ps`는 연달아 돌리면 1번에 약 5ms인데, 2초 간격으로 돌리면 그사이 CPU 클럭이 내려가 약 11ms가 든다(QoS와 무관하게 재현). 창을 열어 둔 동안 `ps` 몫이 0.5%인 이유다.
- WindowServer·제어 센터에 주는 영향은 측정 잡음(2에서 16%p)이 커서 가려내지 못했다. Stats에도 같은 비용이 붙는다.

## 8. 부딪힌 macOS 동작

- **macOS 26에서는 메뉴 막대 칸 창을 제어 센터가 들고 있다.** 내 프로세스에 보낸 합성 클릭(`CGEventPostToPid`)이 칸에 닿지 않아서, 위젯별 클릭·오른쪽 클릭 메뉴는 자동 시험을 못 하고 손으로 확인했다.
- `proc_pid_rusage`·`PROC_PIDTBSDINFO`·`proc_name`은 같은 계정 프로세스만 된다. `PROC_PIDT_SHORTBSDINFO`·`proc_pidpath`·`sysctl KERN_PROC_PID`(시작 시각)는 전부 된다. `sysctl KERN_PROC`의 `p_pctcpu`·`p_rtime`은 0으로만 온다.
- Stats의 SSD 여유 공간은 `statfs`의 f_bavail에 `CSDiskSpaceGetRecoveryEstimate`(비울 수 있다고 추정한 공간)를 더한 값이라, 실제 사용률이 70%일 때 23%처럼 보이고 추정치가 바뀔 때마다 출렁인다. ResourceBar는 f_bavail만 쓴다.
- 프로세스 CPU 시간은 Apple Silicon에서 효율·성능 코어와 클럭에 따라 같은 일도 달라진다. 0.1%p 수준의 차이는 측정 조건에 민감하다.
